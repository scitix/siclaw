# Stop confirmation and assistant lifecycle

The external portal integration must distinguish a requested stop from a drained AgentBox execution. AgentBox already returns `pending:true` for cold starts and abort drain timeouts. The HTTP client now preserves that response. A scoped Runtime `chat.abort` returns `{ok:true, turnId, stopped}`; stopped is true only after a positive non-pending box response. Stale requests retain the existing stale response. A legacy missing-session response does not prove termination. Unscoped callers retain their existing `{ok:true}` contract.

The external portal atomically captures the canceled token and epoch and releases that generation only on matching proof. Its UI separates stopping from working and retains exclusion while stop remains unconfirmed. This also lets a surviving API instance finish an orphaned send's confirmed stop. Normal consumer termination after cancellation is not proof because Runtime breaks its consumer before aborting the box.

Pi carries the same completed assistant on message_end and turn_end. Persist message_end once per step; use turn_end only as a fallback when no assistant message_end occurred in that step. Do not deduplicate by text across steps. The external portal renders complete end-only text and adopts dbMessageId, retaining phase and author for progress and final answers.
